# KV缓存优化

## 为什么需要加速？

现在我们有了一个基本的文本生成函数，我们可以关注实际运行时会发生什么。你可能注意到，前一节的文本生成有点慢。这个缓慢指向一个关键关注点：**推理时的运行性能**。

当使用LLM进行推理时（在这个语境下意味着从提示生成文本），运行性能（效率）很快变得重要，特别是对于长序列。

虽然本书中的代码强调清晰度而非速度，但实际系统经常使用工程技巧来使推理更高效。

## KV缓存介绍

一种能提高文本生成速度的工程技巧是**KV缓存**，其中KV指的是模型注意力机制中使用的键（Key）和值（Value）。

**核心思想：**
我们可以在文本生成的每个步骤缓存某些中间值并重用它们，这有助于加速推理。

### KV缓存的工作原理

#### 传统方法（无缓存）

```
迭代1: [token1, token2, token3] → 模型处理全部
迭代2: [token1, token2, token3, token4] → 模型再次处理全部
迭代3: [token1, token2, token3, token4, token5] → 模型再次处理全部
...
```

每次迭代，新token都与整个输入序列拼接并反复反馈给模型。这种方法效率低下，因为除了新生成的token外，所有token在后续迭代中保持不变。

#### KV缓存方法

```
迭代1: [token1, token2, token3] → 模型处理全部，缓存K和V
迭代2: 只输入 [token4] → 从缓存获取token1-3的K和V
迭代3: 只输入 [token5] → 从缓存获取token1-4的K和V
...
```

KV缓存存储每次迭代中计算的中间值。通过使用KV缓存，我们避免冗余计算，而是直接检索存储的中间表示。

### KV缓存图示

```
无KV缓存：
输入 [t1, t2, t3] → 处理 → 生成 t4
输入 [t1, t2, t3, t4] → 处理 → 生成 t5  (t1-t3重复计算！)
输入 [t1, t2, t3, t4, t5] → 处理 → 生成 t6 (t1-t4重复计算！)

有KV缓存：
输入 [t1, t2, t3] → 处理，缓存K,V → 生成 t4
输入 [t4] → 用缓存K,V → 处理 → 生成 t5
输入 [t5] → 用缓存K,V → 处理 → 生成 t6
```

## generate_text_basic_cache函数

下面是结合了KV缓存的`generate_text_basic`函数修改版本，几乎与基本文本生成函数相同，只是通过注释高亮的KV缓存相关变化：

```python
from reasoning_from_scratch.qwen3 import KVCache

@torch.inference_mode()
def generate_text_basic_cache(
    model,
    token_ids,
    max_new_tokens,
    eos_token_id=None
):
    input_length = token_ids.shape[1]
    model.eval()

    cache = KVCache(n_layers=model.cfg["n_layers"])  # 初始化KV缓存
    model.reset_kv_cache()  # 重置模型内部的KV缓存状态

    # 第一轮，像之前一样提供完整输入给模型
    out = model(token_ids, cache=cache)[:, -1]

    for _ in range(max_new_tokens):
        next_token = torch.argmax(out, dim=-1, keepdim=True)

        if (eos_token_id is not None
            and torch.all(next_token == eos_token_id)):
            break

        token_ids = torch.cat([token_ids, next_token], dim=1)

        # 后续迭代只输入next_token给模型
        out = model(next_token, cache=cache)[:, -1]

    return token_ids[:, input_length:]
```

### 关键差异

`generate_text_basic_cache`函数与`generate_text_basic`函数只有少许不同。主要区别是引入了`KVCache`对象。

**第一次迭代：**
- 像之前一样将完整输入token序列提供给模型，使用`model(token_ids, cache=cache)`
- 在后台，KV缓存为所有这些输入token存储中间值

**后续迭代：**
- 不再需要传递整个序列
- 相反，只使用`model(next_token, cache=cache)`提供`next_token`给模型
- 模型然后从之前存储的KV缓存中检索必要的上下文

## 为什么KV缓存有效？

### 注意力机制回顾

在Transformer的注意力机制中，每个token都会计算与序列中其他所有token的注意力分数。这需要查询（Query, Q）、键（Key, K）和值（Value, V）三个向量。

### 计算开销

```
迭代1: 输入 [t1, t2, t3]
- 计算Q1, Q2, Q3, K1, K2, K3, V1, V2, V3
- 生成 t4

迭代2（无缓存）: 输入 [t1, t2, t3, t4]
- 重新计算Q1, Q2, Q3, K1, K2, K3, V1, V2, V3 (冗余！)
- 计算Q4, K4, V4
- 生成 t5

迭代2（有KV缓存）: 输入 [t4]
- 从缓存获取K1, K2, K3, V1, V2, V3
- 只计算Q4, K4, V4
- 生成 t5
```

### 内存 vs 速度的权衡

**KV缓存的代价：**
- 需要额外的内存来存储中间表示（K和V）
- 内存使用随序列长度增长

**KV缓存的好处：**
- 显著减少计算时间
- 每次迭代只计算新token的表示
- 避免重复计算之前已经计算过的token
