# 1. 大模型推理系统基础

## 1.1 大模型推理流程

典型 LLM 推理流程：

```text
Request
  ↓
Tokenizer
  ↓
Prompt Prefill
  ↓
KV Cache 写入
  ↓
Decode Loop
  ↓
Sampling / Beam Search
  ↓
Detokenizer
  ↓
Streaming Output
```

其中：

- **Prefill 阶段**：对输入 prompt 一次性并行计算，生成初始 KV Cache。
- **Decode 阶段**：逐 token 自回归生成，每一步读取 KV Cache 并追加新的 K/V。
- **KV Cache**：存储历史 token 的 key/value，用来避免重复计算。
- **Scheduler**：决定哪些请求进入 batch、何时 prefill、何时 decode、如何抢占和回收显存。
- **Kernel**：执行底层矩阵乘、attention、RMSNorm、RoPE、MoE、采样等算子。

---

## 1.2 大模型推理的核心瓶颈

主要瓶颈：

| 瓶颈 | 说明 |
|---|---|
| 显存瓶颈 | 权重、KV Cache、激活、中间 buffer 占用巨大 |
| 带宽瓶颈 | Decode 阶段常是 memory-bound |
| 调度瓶颈 | 请求长度不同，静态 batch 会导致 GPU 空转 |
| Attention 瓶颈 | 长上下文时 KV 访问和 attention 计算成本高 |
| 通信瓶颈 | 多 GPU tensor parallel、MoE all-to-all 通信开销大 |
| 冷启动瓶颈 | 模型加载、编译、CUDA Graph 捕获耗时 |
| 长尾延迟 | 长 prompt、长输出、热点前缀、并发突刺导致 p99 抖动 |
| 多租户瓶颈 | 多模型、多 LoRA、多优先级请求争抢资源 |

# 3. 请求调度与批处理技术

## 3.1 静态批处理

传统方式：

```text
等待一批请求凑齐
  ↓
一起执行
  ↓
最长请求完成后释放 batch
```

问题：

- 请求长度不同导致 padding 浪费
- 短请求等待长请求
- GPU 利用率不稳定
- 不适合流式自回归生成

---

## 3.2 Dynamic Batching

思想：

```text
在短时间窗口内聚合请求形成 batch
```

优点：

- 增加吞吐
- 实现简单
- 适合传统模型

缺点：

- 对 LLM decode loop 不够高效
- batch 内请求长度差异仍然浪费
- 可能增加 TTFT

---

## 3.3 Continuous Batching

Continuous Batching 在每个 decode step 动态调整 batch。请求完成后，新请求可立刻加入，不必等待整个 batch 完成。

流程：

```text
Decode step t
  ↓
完成的请求退出
  ↓
新请求进入
  ↓
继续下一步 decode
```

优点：

- 提高 GPU 利用率
- 提升吞吐
- 降低队列等待
- 适合流式 LLM 服务

常见实现：

- vLLM Continuous Batching
- TGI Continuous Batching
- SGLang Continuous Batching
- TensorRT-LLM In-flight Batching

---

## 3.4 In-flight Batching

NVIDIA TensorRT-LLM 常使用 In-flight Batching 术语，核心思想与 Continuous Batching 类似：

- 动态管理正在执行的请求
- prefill 与 decode 可混合调度
- 请求完成后释放资源
- 新请求无需等待旧 batch 完全结束

---

## 3.5 Chunked Prefill

长 prompt 的 prefill 可能阻塞 decode 请求。Chunked Prefill 将长 prompt 切成多个 chunk。

优点：

- 避免长 prompt 阻塞短请求
- 改善 TTFT
- 平衡 prefill 和 decode
- 降低 p99 延迟

相关技术：

- Chunked Context
- Chunked Prefill
- Prefill Scheduling
- Split Prefill
- Interleaved Prefill Decode

---

## 3.6 Prefill-Decode Disaggregation

将 prefill 和 decode 分离到不同资源池：

```text
Prefill Workers：处理长 prompt、大吞吐矩阵计算
Decode Workers：处理逐 token 低延迟生成
```

优点：

- prefill 与 decode 资源特性不同
- 提升资源利用率
- 降低长 prompt 对 decode 的干扰
- 适合超长上下文和高并发

常见于：

- SGLang
- 大规模在线推理集群
- 分布式 LLM serving

---

# 4. KV Cache 管理技术

## 4.1 KV Cache 基础

Transformer 自回归生成中，每层 attention 保存历史 token 的 K/V：

```text
KV Cache Size ≈ batch × layers × heads × seq_len × head_dim × dtype
```

KV Cache 往往成为长上下文推理的主要显存瓶颈。

---

## 4.2 连续 KV Cache

传统 KV Cache 通常为每个请求预分配连续显存。

问题：

- 显存碎片
- 预估长度困难
- 长短请求混合浪费
- 请求结束后回收困难

---

## 4.3 PagedAttention / Paged KV Cache

PagedAttention 将 KV Cache 切成固定大小 block，通过逻辑地址到物理 block 的映射管理。

优势：

- KV Cache 不必连续存储
- 减少显存碎片
- 支持更大 batch
- 动态分配与回收
- 类似操作系统虚拟内存分页

代表实现：

- vLLM PagedAttention
- TGI Paged Attention
- TensorRT-LLM Paged KV Cache
- SGLang Paged Attention

---

## 4.4 Prefix Caching

Prefix Caching 复用相同 prompt 前缀的 KV Cache。

适用：

- 系统提示词固定
- RAG 模板固定
- 多轮对话共享历史
- Agent 工具调用模板
- 批量评测同一 instruction

技术：

- Exact Prefix Match
- Hash-based Prefix Cache
- Token-level Prefix Cache
- Block-level Prefix Cache
- Multi-tenant Prefix Cache
- Prefix Cache Eviction

---

## 4.5 RadixAttention

SGLang 的 RadixAttention 使用 radix tree 管理前缀 KV Cache，实现自动共享和复用。

思想：

```text
请求 prompt → token prefix → radix tree 匹配 → 复用已有 KV Cache
```

优势：

- 自动发现公共前缀
- 减少重复 prefill
- 适合多轮对话和 RAG
- 对 Agent 工作流友好

---

## 4.6 KV Cache 量化

目的：

- 降低显存占用
- 支持更长上下文
- 提升 batch 容量

方法：

- INT8 KV Cache
- FP8 KV Cache
- INT4 KV Cache
- Per-tensor KV Quantization

- Mixed-precision KV Cache
- Quantized Paged KV Cache

权衡：

- 显存降低
- 可能影响长上下文质量
- 需要校准和误差分析

# 5. Attention 推理优化

## 5.1 标准 Attention 瓶颈

Attention 计算：

```text
Attention(Q,K,V) = softmax(QK^T / sqrt(d)) V
```

瓶颈：

- 长上下文 O(n²)
- KV Cache 读带宽大
- Decode 阶段 batch 小且 memory-bound
- 显存访问远比计算更关键

---

## 5.2 FlashAttention

FlashAttention 通过 IO-aware tiling 减少 HBM 读写，避免显式存储完整 attention 矩阵。

特点：

- 分块计算
- 利用 SRAM / shared memory
- 降低显存读写
- 支持长序列
- 提高 attention 吞吐

相关版本：

- FlashAttention
- FlashAttention-2
- FlashAttention-3
- Flash Decoding
- FlashInfer Attention

---

## 5.3 PagedAttention Kernel

特点：

- 支持 paged KV block
- 通过 block table 访问 K/V
- 适合 continuous batching
- 减少内存碎片
- 支持动态 batch

常见于：

- vLLM
- TGI
- TensorRT-LLM
- SGLang

---

## 5.4 FlashInfer

FlashInfer 是面向 LLM serving 的 kernel 库，常用于：

- Attention
- Paged KV Cache
- Decode
- Prefill
- Cascade Attention
- Batch Decode
- Sampling
- MoE
- KV Layout 优化

---

## 5.5 FlashMLA / MLA Attention

适用于 DeepSeek 等使用 MLA 的模型。

技术点：

- Multi-head Latent Attention
- KV 压缩表示
- MLA Decode Kernel
- FlashMLA
- FP8 / BF16 混合
- Page-based KV

---

## 5.6 MQA / GQA

目的：

- 降低 KV Cache 大小
- 降低 decode 阶段显存带宽

类型：

- Multi-Head Attention
- Multi-Query Attention

对比：

| 类型 | KV 头数 | 显存占用 | 质量 |
|---|---|---|---|
| MHA | 多个 K/V 头 | 高 | 高 |
| MQA | 一个 K/V 头 | 低 | 可能下降 |
| GQA | 分组 K/V 头 | 中 | 较好 |
| MLA | 潜变量压缩 KV | 低 | 依模型而定 |

# 6. 解码与采样加速

## 6.1 自回归解码

LLM 逐 token 生成：

```text
token_t = model(token_<t)
```

问题：

- 串行依赖强
- 每步只生成一个 token
- decode 阶段 GPU 利用率低
- 受 KV Cache 读带宽限制

---

## 6.2 Speculative Decoding

使用小 draft model 先生成多个候选 token，再用大 model 验证。

流程：

```text
Draft Model 生成 k 个 token
  ↓
Target Model 并行验证
  ↓
接受部分 token
  ↓
继续下一轮
```

优点：

- 减少大模型 forward 次数
- 保持分布一致性
- 提升 decode 吞吐

相关方法：

- Speculative Sampling
- Assisted Generation
- Draft-Verify Decoding
- Multi-token Prediction
- EAGLE
- Medusa
- Lookahead Decoding
- REST
- SpecInfer
- n-gram Speculation
- Prompt Lookup Decoding

---

## 6.3 Medusa

思想：

- 在主模型上增加多个 decoding heads
- 一次预测多个未来 token
- 用 tree attention 验证候选

优点：

- 不一定需要独立 draft model
- 可减少延迟
- 适合模型微调

---

## 6.4 EAGLE

思想：

- 基于特征层预测未来 token
- 使用轻量预测头生成候选
- 目标模型验证

适用：

- 大模型加速
- 保持生成质量
- 可与 serving engine 结合

---

## 6.5 Lookahead Decoding

思想：

- 在解码时探索多个候选路径
- 通过并行验证减少串行步数

技术：

- Tree Decoding
- Parallel Verification
- Candidate Expansion
- Acceptance Check

---

# 27. 总结

大模型推理引擎、算子开发、算子优化和推理加速可以概括为以下大类：

1. **推理服务引擎**：vLLM、SGLang、TGI、TensorRT-LLM、Triton、llama.cpp、MLC LLM  
2. **请求调度**：Dynamic Batching、Continuous Batching、In-flight Batching、Chunked Prefill、Prefill/Decode 分离  
3. **KV Cache 管理**：PagedAttention、Paged KV Cache、Prefix Cache、RadixAttention、KV 量化、KV 压缩与 offload  
4. **Attention 优化**：FlashAttention、PagedAttention Kernel、FlashInfer、FlashMLA、MQA/GQA/MLA、长上下文 attention  
5. **解码加速**：Speculative Decoding、Medusa、EAGLE、Lookahead、Prompt Lookup、Tree Decoding  
6. **算子开发**：CUDA、Triton、CUTLASS、cuBLASLt、TensorRT Plugin、TVM TensorIR、PyTorch Extension  
7. **算子优化**：融合、分块、向量化、Tensor Core、shared memory、寄存器、CUDA Graph、persistent kernel  
8. **编译器优化**：TorchInductor、TensorRT、TensorRT-LLM、TVM、XLA、MLIR、ONNX Runtime、OpenVINO  
9. **量化压缩**：FP8、FP4、INT8、INT4、AWQ、GPTQ、SmoothQuant、GGUF、KV Cache 量化  
10. **分布式推理**：Tensor Parallel、Pipeline Parallel、Expert Parallel、Context Parallel、多节点 NCCL/RDMA  
11. **MoE 推理**：Expert Routing、Grouped GEMM、All-to-All、DeepEP、Load Balancing  
12. **LoRA 推理**：Multi-LoRA、LoRA 热加载、LoRA 合批、Adapter Routing  
13. **多模态推理**：视觉 token 压缩、视频采样、多模态 encoder cache、多模态 batch  
14. **RAG / Agent 优化**：Prefix Cache、RadixAttention、结构化输出、工具调用缓存、上下文压缩  
15. **本地与边缘推理**：llama.cpp、GGUF、MLC、Ollama、Core ML、Metal、Vulkan、NPU  
16. **监控评测**：TTFT、TPOT、吞吐、显存、KV cache、p99、tokens/s、成本/token  

一句话总结：

> 大模型推理加速的本质是：在保证生成质量的前提下，通过“更聪明的调度、更高效的 KV Cache、更快的 attention kernel、更低精度的计算、更合理的并行与更工程化的服务架构”，把每一块 GPU 的 token 产出效率最大化。
